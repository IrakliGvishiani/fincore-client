# FinCore Client — Angular frontend

Graduation project: digital banking simulator. This repo is the **Angular 19** frontend only.

## Hard rules
- **Backend is READ-ONLY**: `C:\Users\user\source\repos\FinCore` (ASP.NET Core, Clean Architecture). Never modify it. The owner fixes backend issues personally.
- All changes go into this repo (`fincore-client`).
- Work module by module; stop after each step for the owner's review.
- Do not invent endpoints. If the backend lacks something, leave it out of the UI.
- Reset password: the backend emails a link to `{FrontendBaseUrl}/reset-password?email=&token=` (see Auth). Email and token come only from that link (no manual entry).

## Stack decisions
- Angular 19, standalone components, signals, functional interceptors/guards, lazy `loadComponent`/`loadChildren`.
- Angular Material (M3 theme in `src/styles.scss`), Chart.js 4 via **ng2-charts 8** (installed in step 10; registered per component with `provideCharts({registerables})` in the lazy analytics chunk only).
- English UI only.
- Dev: backend runs in Docker on `http://localhost:8080`; `ng serve` proxies `/api` there via `proxy.conf.json` (same-origin, so CORS is not involved). The backend now has a CORS policy allowing only `AppSettings:FrontendBaseUrl` (default `http://localhost:4200`); prod should still be same-origin (nginx serves SPA + proxies `/api`).

## Backend conventions (verified from code)
- Envelope: every response is `{ message, result, isSuccess, statusCode }` (camelCase); payload is in **`result`**.
- Enums serialized as **names** (PascalCase): `GEL|USD|EUR|GBP`; AccountStatus `Active|Frozen|Closed`; TransferStatus `Pending|Completed|Failed|Cancelled`; EntryType `Debit|Credit`; TransferDirection `Outgoing|Incoming`; VirtualCardStatus `Active|Frozen|Closed|Expired`; SimulatedPaymentStatus `Pending|Completed|Failed`; PaymentDeclineReason `CardNotActive|CardExpired|AccountNotActive|TransactionLimitExceeded|DailyLimitExceeded|InsufficientFunds|CurrencyMismatch`; SuspiciousActivityStatus `Detected|UnderReview|Resolved`; RiskLevel `Low|Medium|High` (<30, <60, ≥60).
- Dates are UTC but serialized **without `Z`** → always parse via `parseUtc()` / `utcDate` pipe.
- Amounts: max 2 decimals.
- **204 responses: treat as success with no body. Never rely on a body.**
- Paging params always `pageNumber`, `pageSize` (max 100). Four response shapes (normalized by `ApiClient.getPaged`): `{items,totalCount}`, `{items,totalcount}` (conversions), `{items,totalCount,pageNumber,pageSize}` (admin users), `PaginatedResult` with `totalPages` (cards, payments, manager).
- Date filters: `toDate` is inclusive (server adds 1 day) on statement, conversions, audit, manager lists. **Analytics `toDate` is exclusive** and both dates are required.
- Roles: `Customer`, `Manager`, `Admin`. Customer-only controllers return 403 for Manager/Admin.

- `POST auth/register-manager`, `POST auth/register-admin` (**Admin**) same body
- `POST auth/confirm-email` `{email,code}` (6 digits, 5 min) · `GET auth/resend-confirmation-code?email=` (1/60s, 5/h)
- `POST auth/login` `{userName: <email>, password}` → `{accessToken,refreshToken}`
- `POST auth/refresh-token` body = **raw JSON string** → new pair (rotation: old token deleted). Invalid → **400**.
- `POST auth/forgot-password` body = raw JSON string email · `POST auth/reset-password` `{email,token,newPassword}`
- `POST auth/revoke-token` body = raw JSON string refresh token (400 if already gone → ignore)

**account** (Customer; controller-level `[Authorize(Roles = Customer)]`): `GET account` → AccountForGettingDto[] `{id,accountNumber,name,balance,currency,status,createdAt}` (`id` confirmed in code) · `GET account/{no}` (404 "Account not found" for other users) · `GET account/{no}/statement?from&to&pageNumber&pageSize(15, max 100)` → `{items,totalCount}`, newest first; entries `{ledgerEntryId,reference,type,amount,currency,createdAt}`; **Credit = money in, Debit = money out** on the customer account; `from`/`to` are compared with UTC `CreatedAt` (`to` + 1 day), so day boundaries are UTC days · `POST account?currency=&name=` (**query params**, no body; name optional ≤50, default "<CUR> account"; max 5 non-closed → 400 "You can only have up to 5 open accounts.") → `{accountNumber,createdAt}` · `POST account/{no}/close` (Active **and** balance 0, else domain error; 204) · `PATCH account/{no}/name` body `{name}` (1–50; not on Closed) → AccountForGettingDto · `POST account/{no}/deposit` header `Idempotency-Key` (≤50) body `{amount}` (`[Range(0.01, 10100)]`, 2 decimals; Active only) → AccountForGettingDto. Replay with the same key + amount returns the account (the owner fixed the old always-409 bug: it now looks for the customer Credit + cash Debit entries); a different amount → 409 "IdempotencyKey has already been used for a different deposit" · `GET account/analytics?fromDate&toDate` (see **analytics** below)

**transfers** (Customer): `GET transfers?pageNumber&pageSize` (default 10, max 100; no filters) → `{items: MyTransferDto[], totalCount}` newest first; MyTransferDto `{id,direction,counterPartyAccountNumber,myAccountNumber,amount,currency,status,description,createdAt}` · `GET transfers/{id:int}` → TransferDto `{id,fromAccountNumber,toAccountNumber,amount,currency,status,description,createdAt,completedAt,failureReason}` (404 "Transfer not found!" if not yours) · `POST transfers/recipients/lookup` `{personalNumber}` (`^d{11}$`) → `[{accountId,maskedAccountNumber (last 4 visible),currency}]` of the person's **Active** accounts; unknown person or no active accounts → 404; rate limit 1/s and 20 per 10 min returns **400 "Too many lookups. Please try again later"** (no 429 anywhere in the backend); the lookup also returns your own accounts if you enter your own number · `POST transfers/by-account-number` header `Idempotency-Key` (≤100) `{fromAccountNumber(≤20),toAccountNumber(≤20),amount([Range(0.01,1000000)], 2 decimals),description?(≤500, trimmed, blank → null)}` (unknown destination → 404 "Destination account not found.") · `POST transfers/by-recipient` same header `{fromAccountNumber,toAccountId(≥1),amount,description?}` · both → TransferDto. Rules: transfer currency = source currency; different currencies → 400 "Source and destination accounts must use the same currency."; same account, insufficient funds ("Insufficient funds."), inactive source/destination ("Cannot debit from / credit to an inactive account.") are domain errors → **500 with the message**, and the whole transaction is rolled back, so failed transfers are **not stored**: a successful response is always `Completed` (Pending/Failed/failureReason exist in the model but this flow never returns them). Same key + same payload returns the original transfer; same key + different payload → 409 "Idempotency key already used for a different transfer." · `GET transfers/{id:int}/receipt` → FileContentResult (PDF, base64). **Masking** (TransferService.MaskAccountNumber, `**************1234`, last 4 visible): history `counterPartyAccountNumber` is masked, `myAccountNumber` full; TransferDto (detail, by-account-number, by-recipient) has `fromAccountNumber` **full** and `toAccountNumber` **always masked**, even when the destination is my own account (incoming transfers, transfers between my accounts), so an incoming transfer shows the sender's full number and my own account masked; the receipt PDF does the same (From full, To masked). The UI shows masked numbers as `•••• 1234` (`accountNumber` pipe) and hides the copy button for them.

**conversions** (Customer; `ConversionController`): `POST conversions/quote` `{fromAccountNumber,toAccountNumber,amount([Range(0.01,1000000)])}` → ConversionQuoteDto `{fromAccountNumber,toAccountNumber,fromAmount,fromCurrency,toAmount,toCurrency,rate,feeRate,feeAmount,netAmount,rateDate}`. Both accounts must be mine (else 404 "Source/Destination account not found."), **any status** (the quote checks neither status nor balance); same currency → 400 "Currencies must be different"; too small → 500 "Amount is too small to convert.". Math (CurrencyConversion.Create): `feeAmount = round(fromAmount × feeRate, 2, away from zero)` in the **source** currency; `netAmount = fromAmount − feeAmount` (**source** currency, the amount actually converted); `toAmount = round(netAmount × rate, 2, toward zero)` = what the target account **receives**. `rate` = target units per 1 source unit (8 decimals); `rateDate` = NBG `validFromDate` (an official calendar day → show the date part only). Rates cached in memory 30 min; NBG failure → 503 "Exchange rates are temporarily unavailable."; currency missing in the NBG table → 400 "Rate for X is not available". · `POST conversions` header `Idempotency-Key` (required, ≤100, else 400) `{fromAccountNumber,toAccountNumber,amount,expectedRate?}` → ConversionDto (quote fields + `id`, `createdAt`). Server order: load accounts → current rate → **expectedRate ≠ rate → 409 "The exchange rate has changed. Please confirm the new rate."** → idempotency lookup (same key + accounts + amount → original conversion; else 409 "Idempotency key already used for a different conversion.") → execute (inactive account, "Insufficient funds." → 500 with message, rolled back). Because the rate check runs first, retrying a conversion that already succeeded can get the rate-changed 409, so the client keeps the same key across the re-quote. · `GET conversions?fromDate&toDate&fromCurrency&toCurrency&pageNumber&pageSize` (default 10, max 100 else 400; fromDate > toDate → 400; `toDate` inclusive; compared with UTC `CreatedAt`) → `{items: ConversionDto[], totalcount}` (**lowercase** key, handled by `normalizePaged`), newest first; account numbers are my own, full. · `GET conversions/{conversionId:int}/receipt` → FileContentResult PDF (404 "Conversion not found."). **There is no `GET conversions/{id}`** (no detail page).

**card** (Customer, singular; `VirtualCardController`, no DTO validation attributes, rules in `VirtualCard`): `POST card` `{bankAccountId(required),name,dailyLimit,transactionLimit}` → **200** (not 201) VirtualCardCreatedDto `{id,cardNumber,last4Digits,expiryMonth,expiryYear,dailyLimit,transactionLimit}`. The 16-digit (Luhn, starts with 9) **cardNumber exists only in this response**: the server stores only `last4Digits`. Rules: account must be mine (404 "Bank account not found") and **Active** ("Card requires an active account."); name non-blank ≤ 50 (trimmed); limits > 0, transaction ≤ daily, daily ≤ 100,000 (no decimals check on limits); expiry = now + 3 years (month/year). Domain errors → 500 with the message. · `GET card?pageNumber&pageSize` (**always send both**: no defaults) → PaginatedResult `{items,totalCount,pageNumber,pageSize,totalPages}` newest first · `GET card/{cardId:int}` → VirtualCardDto `{id,bankAccountId,name,last4Digits,expiryMonth,expiryYear,status,dailyLimit,transactionLimit,createdAt}` (404 "Virtual card not found") · `PATCH card/{id}/limits` `{dailyLimit,transactionLimit}` (not on Closed) · `PATCH card/{id}/freeze` (Active only) · `/unfreeze` (Frozen only) · `/close` (anything but Closed; permanent) — all **204**. The backend **never sets `Expired`**: expiry is only checked when paying (unusable from the 1st of the month after the expiry month, UTC), so the UI derives "Expired" from the date (`displayStatus`).

**payments** (Customer; `SimulatedPaymentController` — **no `[ApiController]`**, so no automatic model validation): `POST payments` `{virtualCardId,amount,merchant,description?,idempotencyKey}` (key in the **body**, ≤ 100) → **200** PaymentDto `{id,virtualCardId,merchant,description,amount,currency,status,failureReason,reference,last4Digits,createdAt}`. **No currency in the request: the payment is always in the card's account currency** (`card.Authorize(account, amount, account.Currency, …)`), so `CurrencyMismatch` can never occur today; a price in another currency would simply be charged as that number in the account's currency. Checks in order (each → `status: Failed` + `failureReason`, **stored**, HTTP 200): card not Active → CardNotActive; past expiry → CardExpired; account not Active → AccountNotActive; amount > transactionLimit → TransactionLimitExceeded; spent today (Completed, since UTC midnight) + amount > dailyLimit → DailyLimitExceeded; amount > balance → InsufficientFunds. Amount ≤ 0 or > 2 decimals, blank merchant / > 100 → 500 domain error; description > 500 only fails in the DB. Idempotency is per **card** (`VirtualCardId + key`): same key with same amount + trimmed merchant + trimmed description returns the stored payment (also a stored decline); different → 409 "Idempotency Key already used for a differenc payment" (typo in backend). Unknown card → 404 "Virtual card not found" (checked before the idempotency lookup). Re-checked for step 9: no amount maximum on the server (only the card limits, so over-limit amounts are declines, not errors); the key is trimmed by the server; blank key → 500 "Idempotency key is required."; the action has an extra `[Authorize]` but the controller-level Customer role still applies. · `GET payments?pageNumber&pageSize` (defaults 1/10) all my cards' payments newest first · `GET payments/{paymentId:int}` · `GET payments/card/{cardId:int}?pageNumber&pageSize` · all paged → PaginatedResult · `GET payments/{paymentId:int}/receipt` → FileContentResult PDF (also for declined payments; 404 "Payment not found.").

**analytics** (Customer; `BankAccountController` `[ApiController]`, `AnalyticsService` + `AnalyticsRepository`, verified in step 10): `GET account/analytics?fromDate&toDate` (both `DateTime`, both required in practice: a missing one binds as `DateTime.MinValue`) → `{fromDate, toDate, currencies: [{currency, balance, income, expenses, netCashFlow}], monthlyBreakdown: [{year, month, currency, income, expenses, netCashFlow}]}` (`netCashFlow` = income − expenses, computed property). `fromDate >= toDate` → 400 "From date must be earlier than to date.". Filter: ledger entries of my accounts with `CreatedAt >= fromDate && CreatedAt < toDate` — **toDate exclusive, used literally** (no +1 day). The client sends `yyyy-MM-dd`; ASP.NET binds it as midnight without a zone and it is compared with UTC `CreatedAt`, so **days are UTC days**; the monthly breakdown is grouped by UTC `CreatedAt` year/month and **only months with entries are returned** (client fills zeros), ordered year → month → currency; a month row can be all zero (e.g. only conversions). **What counts** (any account status, all my accounts): income = Deposit credits + Transfer credits where sender and receiver are **different users**; expenses = CardPayment debits + Transfer debits to a **different user**. **Not counted:** currency conversions, transfers between my own accounts. **`balance`** = the **current** balance (not at the period end) summed over my **non-Closed** accounts (Active **and Frozen**) in that currency, independent of the dates. `currencies` contains every currency that has a non-closed account or ledger activity in the period (zeros otherwise), in no particular order. No categories, merchants or per-account split exist (so the UI shows none).

**recipient** (Customer; `SavedRecipientController`): `GET recipient` → `[{id,name,accountNumber,firstName,lastName,profilePhotoUrl,createdAt}]` ordered by name; owner fields come from a left join on **any** bank account with that number (any status), else null · `POST recipient` `{name,accountNumber}` → 201 SavedRecipientDto **with owner fields always null** (re-read the list). No DTO validation attributes: the server only trims the account number (no format or existence check) and does **not** trim the name; limits exist only in the DB (name ≤ 100, accountNumber ≤ 20 → longer = 500). Duplicate (per user) → 400 "This Recipient is already saved."; a racing duplicate hits the unique index → 409 (default message). Blank name → `ArgumentException` → 500 "Recipient name is required." · `PUT recipient/{id:int}` `{name}` (trimmed) → result is the plain string "updated successfully" · `DELETE recipient/{id:int}` → result "deleted successfully". What `entityId` holds: BankAccount → account **number**, Transfer → transfer id, CurrencyConversion → conversion **reference** (not the id), User → user id, VirtualCard → card id. Who is in `userId`: the acting customer for customer actions; **null** for freeze/unfreeze (the admin is not recorded); for ban/unban the **banned user**, not the admin.
- `PATCH admin/{accountNumber}/freeze` · `PATCH admin/{accountNumber}/unfreeze` (by account **number**, directly under /admin) → 204. Domain: freeze only Active ("Only active accounts can be frozen."), unfreeze only Frozen ("Only frozen accounts can be unfrozen."); unknown → 404 "Account Not Found". **No reason field.**
- `GET admin/users?search&pageNumber&pageSize` (default 1/20) → `{items: UserListItemDto[], totalCount, pageNumber, pageSize}`; `search` (trimmed) = **contains** on first name, last name, email or personal number; sorted last name → first name → id; all roles. UserListItemDto `{id,firstName,lastName,email,personalNumber,phoneNumber|null,profilePhotoUrl|null,createdAt,roles: string[],isBanned}` — `isBanned` (added by the owner after step 12) = `IsAdminLocked`, an **administrator ban only** (not password lockouts). No server-side banned filter. page < 1 or size outside 1–100 → `ArgumentOutOfRangeException` → **500**.
- `GET admin/user/{userId}` (singular) → UserDetailsDto = list item + `bankAccounts: [{accountNumber,currency,balance,status,createdAt}]` (currency/status as plain strings; **no account id**, so the UI links by account number). Blank id → 400, unknown → 404 "User not found".
- `PATCH admin/users/{userId}/ban` → 204: Identity lockout until now + 100 years and `IsAdminLocked = true`; a user with the **Admin** role → 400 "Admin users cannot be banned through this operation."; unknown → 404 "User not found". Banned users cannot sign in (login checks the lock). `PATCH admin/users/{userId}/unban` → 204, clears the lockout; allowed for anyone (also not-banned users and admins).
- `POST auth/register-manager` / `POST auth/register-admin` (`[Authorize(Roles = Admin)]`, same body and validation as register) → **201** with the new user id (string); the backend emails a 6-digit confirmation code, and the new staff member must confirm the email (the login redirects unconfirmed users to /confirm-email) before signing in.
- No role-change, no banned filter, no account lookup by id for admins (the manager endpoints are used).
- **Banned users' sessions** (FinCore working copy, `Program.cs` `JwtBearerEvents.OnTokenValidated` + `UserBanCache` in Redis): a still-valid access token of a banned user is rejected → **401** (empty body); `POST auth/refresh-token` for a banned user → **400** "Invalid or expired refresh token." (and the refresh token is consumed). The ban cache fails open if Redis is down.

**Receipts** come as JSON: `result = { fileContents: <base64>, contentType, fileDownloadName }` → decode with `core/util/download.ts`.

## Auth flow
- **Root "/" and startup:** `/` for guests = `LandingPageComponent` (`features/landing`, lazy; `canMatch: guestOnlyMatch`): public header (logo, Log in, Register), hero, 6 feature cards (`LANDING_FEATURES`), footer with the current year; landmarks + skip link. Signed in → the landing route does not match and the shell's `'' → homeRedirect` sends Customer → `/dashboard`, Manager/Admin → `/manager`. The auth-card layout route has `canMatch: nonEmptyUrlMatch` (never the bare `/`: an empty-path parent with children used to match `/` with no child and showed an **empty card**); its logo and "Back to home" link go to `/`. Startup: `withEnabledBlockingInitialNavigation()` delays bootstrap until the first page is routed while `index.html` shows a static "Loading FinCore…" spinner inside `<app-root>`. **Angular runs app initializers in parallel and the blocking initial navigation starts in one of them**, so the restore initializer alone does NOT order things: **every guard (`authGuard`, `guestGuard`, `roleGuard`, `guestOnlyMatch`) first `await`s `AuthService.whenSessionReady()`** (the memoized `restoreSession()` promise, never rejects). Without that, F5 sent signed-in users to `/login?returnUrl=` although the refresh returned 200 (fixed; `root-routing.spec.ts` "F5 / startup session restore" reproduces it). A reload keeps the same URL incl. deep links/query strings; `/` goes to the role home with no landing flash. Unknown URLs → not-found page with "Go to home" (`/`, works signed in or out). Tested in `root-routing.spec.ts` (real route config, lazy pages stubbed).
- Login with email as `userName`. JWT claims: `sub`, `email`, `role` (string or array), `exp`. Name/photo come from `GET profile`.
- Access token 15 min (**memory only**); refresh token 7 days (**sessionStorage**). On app start, a stored refresh token restores the session. **Authenticated = an access token is stored** (`isAuthenticated()` from the JWT claims); the profile loads afterwards and never gates a guard. **Only a rejected refresh (400/401, `isRefreshRejection`) clears the session.** A network error / 5xx keeps the refresh token: at startup `restoreFailed()` is set and protected routes go to `/session-unavailable?returnUrl=` ("Can't reach FinCore", Try again → back to the page; rejection → /login); while running, the interceptor rethrows the refresh's network error instead of the 401.
- Refresh is single-flight (one request in flight; others wait). Rotation means a reused token fails.
- 401 on an authenticated request → refresh once → retry; refresh rejected (400/401, e.g. a **banned** user) → `AuthService.expireSession()`: clear session, one info toast "Your session has ended. Please sign in again." (`SESSION_ENDED_MESSAGE`), → `/login?returnUrl=`. It runs **once per session** (`sessionEnded`, reset by the next login/restore; also set by logout), so parallel or late 401s add no second toast/redirect; the refresh call itself is `skipAuth` + `silent` (no loop, no error toast). Tested in `core/auth/session-end.spec.ts`. 401/403 from JWT middleware have **empty bodies**. 403 → toast/forbidden page, no logout.
- Logout → `revoke-token` (ignore errors) → clear → `/login`.
- Login errors: 404/400 → generic "Invalid email or password", **except** "Email is not confirmed." (→ confirm page) and locked/banned messages (show as-is). Matching lives in `core/api/error-messages.ts`.
- Password policy (Identity): ≥10 chars, upper, lower, digit, symbol. Phone `+995XXXXXXXXX`. Personal number 11 digits.

## Error handling
- Exception responses: CommonResponse with `message` (404, 400, 405, 401, 409, 503, and **500 for domain-rule errors**, still meaningful messages).
- **Seen in step 11 (FinCore working copy, uncommitted `ErrorHandlingMiddleware.cs`):** `DomainException` and `InsufficientFundsException` now map to **400** (not 500); other unhandled exceptions (e.g. `InvalidOperationException`, `ArgumentException`) are still 500 and still carry `ex.Message` (a `message` variable with "An unexpected error occurred." is computed but not used). The client does not depend on 400 vs 500 for these: it shows meaningful messages either way, and "may have gone through" only applies to 409 / network / 5xx with no meaningful message. Per-endpoint notes above that say "500 with the message" for domain errors predate this change.
- Model validation: ValidationProblemDetails `{title, status, errors: {Field: [msgs]}}`.
- `ApiError` normalizes both; the error interceptor toasts unless the request sets `SILENT_ERROR`. Generic fallbacks for 500/409 when the message is empty or a default .NET text.

## Special requirements
- Idempotency: `newIdempotencyKey()` (UUID) per user intent; reuse on retry/double-click; regenerate after success or when inputs change.
- Every `<form>` must have `[formGroup]` (with `(ngSubmit)`): only FormsModule's NgForm or FormGroupDirective turn a submit into `ngSubmit` and prevent the native submit, and FormsModule is not used here; a bare `<form (ngSubmit)>` reloads the page (the step 8 edit-limits bug).
- `rowVersion` is not exposed; concurrency shows as 409 → generic message.
- Statement export: **client-side CSV** (fetch all pages for the range, pageSize 100, sequentially; cap 10,000 rows with a confirm warning above it; cancellable; columns Date (local), Type, signed Amount, Currency, Reference, Entry ID; UTF-8 BOM). No PDF.
- Hidden for now (no backend): change password, scheduled transfers, transfer filters, role changes, manager user search, a banned filter for the user list, a reason for freezing.
